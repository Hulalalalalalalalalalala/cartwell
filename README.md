# inkseal

当前版本提供命令行版本查询、单文件 SHA-256 摘要计算，以及用已保存的
摘要核对文件内容。

## 构建与运行

```sh
cargo build --offline
./target/debug/inkseal --version
```

输出：

```text
inkseal 0.1.0
```

版本行同样适用输出失败规则：该行无法完整写到标准输出时退出码 `1`，
并在标准错误给出写入失败提示，而非崩溃或报告成功。

## 计算文件摘要

```sh
./target/debug/inkseal digest <文件路径>
```

每次调用只处理一个文件。命令读取指定文件的原始字节，以流式方式计算
SHA-256（内存占用不随文件大小增长），并在标准输出写出恰好 64 个小写
十六进制字符，以换行结束，不附带文件名或标签：

```text
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
```

摘要只取决于文件的原始字节，不包含文件名、路径或时间信息：相同内容
存放在不同位置得到相同结果；空文件得到标准空字节序列的摘要（即上面
所示值）。零字节、非 UTF-8 数据和各种换行形式都原样参与计算，不做
文本解码或换行转换。路径中的空格和非 ASCII 字符按实际路径处理。

命令行参数按操作系统提供的原始字节接收，因此文件名不是合法 UTF-8
的路径同样支持：在允许这类文件名的系统上，它们与普通路径没有区别，
摘要规则完全一致——只对文件原始字节计算，路径中不可解码的字节、
空格和非 ASCII 字符都不参与摘要。命令始终用真实路径访问文件，即使
两个路径只在不可解码的字节上不同，也会分别打开各自对应的文件，不会
因错误信息里显示成相同文字而读错对象。

### 失败与退出状态

- 成功：退出码 `0`，摘要写到标准输出。
- 文件不存在、无法打开、路径指向目录或读取中途失败：退出码 `1`，
  标准输出保持为空，标准错误给出原因并指出出错路径，例如
  `inkseal: cannot open 'nope': No such file or directory (os error 2)`。
  即使已读取部分内容，也不会输出部分内容的摘要。路径无法完整解码为
  Unicode 时，错误信息中的路径以替换字符（U+FFFD）等可见形式呈现，
  仍可辨认且不会导致命令崩溃；该显示文本只用于提示，不会被当作实际
  路径访问。
- 缺少文件路径、多给路径、未知子命令等用法错误：退出码 `2`，
  只在标准错误给出用法提示。
- 摘要已算出但结果无法完整写到标准输出（例如重定向目标拒绝写入，
  或管道接收方提前关闭）：退出码 `1`，只在标准错误给出一行
  `inkseal: unable to write to standard output: <系统原因>`。这不被
  说成读取失败，也不会把摘要改写或补写到标准错误；标准输出可能已
  收到结果的前几个字节，失败后不会重试整行。若连该提示也无法写出，
  仍以退出码 `1` 静默结束，不打印崩溃信息。
- 以上任何失败提示本身无法写到标准错误（例如标准错误被接到另一个
  程序而接收方提前关闭管道，或从一开始就拒绝写入），都不会改变命令
  对本次操作的判断：用法错误仍是退出码 `2`，文件访问失败和摘要不
  匹配仍是退出码 `1`。命令以对应退出码正常结束，不出现崩溃信息，
  不改报成功，也不把错误提示或用法说明转移到标准输出；已经送出的
  提示字节保留，无法写出的内容不补齐，这些情况下标准输出仍为空。
  反之，标准错误不可用本身不影响成功操作：结果仍照常写到标准输出
  并以 `0` 退出。

## 核对文件摘要

```sh
./target/debug/inkseal check-digest <文件路径> <预期摘要>
```

每次调用只接收一个文件和一个摘要。命令只读取文件，不改写它，也不
创建任何结果文件。预期摘要必须恰好由 64 个 ASCII 十六进制字符组成，
大小写均可，比较时按它表示的 32 字节摘要值判断。**不自动去掉空白**：
带前缀（如 `0x`）、夹有空格、末尾带换行、长度不对或出现非十六进制
字符，都属于用法错误。摘要参数无法解码为合法文字时同样是用法错误。

**格式校验先于文件访问**：摘要不合法时不会打开文件——即使给出的路径
也不存在，仍报告摘要格式问题。

### 匹配时

退出码 `0`，标准错误为空，标准输出只写 `OK` 加一个换行：

```text
OK
```

只有 `OK\n` 完整写出才算匹配成功；写出失败（重定向目标拒绝写入、
管道接收方提前关闭等）时退出码 `1`，按 `digest` 一节相同的输出
失败规则在标准错误给出提示，不补写 `OK`，也不报成内容不匹配。

### 不匹配时

退出码 `1`，标准输出为空，标准错误明确说明内容不匹配，并同时列出
预期摘要和实际摘要，两者都以 64 个小写十六进制字符显示：

```text
inkseal: digest mismatch for 'docs/report.pdf'
expected: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
actual:   ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
```

### 文件访问失败时

文件不存在、指向目录、无法打开或读取中途失败时退出码也是 `1`，但
提示指出出错路径和具体原因（如 `cannot open`、`cannot read`），不会
把它说成内容不匹配，也不会给出部分内容或整个文件的实际摘要。

### 内容规则

核对沿用 `digest` 的内容规则：只比较原始字节，不把文件名、路径和
时间算进摘要，不转换文本或换行，空文件同样可以核对（空文件的摘要
为 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`）。
大文件仍以流式读取计算，内存占用不随文件大小增长。文件路径按操作
系统提供的实际路径访问，包括支持这类名称的系统上的非 UTF-8 文件名；
错误提示里的路径显示沿用 `digest` 的现有规则。

### 用法错误

缺少参数、多给参数、摘要参数无法解码为合法文字，或摘要不符合
64 个十六进制字符的格式：退出码 `2`，标准输出为空，标准错误说明
输入问题并给出用法。

## 用保存的摘要文件核对

`digest` 的摘要行可以直接重定向保存成文件，之后不必再把那一串字符
复制到参数里，用 `check-digest-file` 直接读取摘要文件核对：

```sh
./target/debug/inkseal digest report.pdf > report.sha256
./target/debug/inkseal check-digest-file report.pdf report.sha256
```

每次调用只核对一个文件。命令只读取待核对文件与摘要文件，不改写其中
任何一个，也不创建结果文件。匹配时退出码 `0`、标准错误为空、标准输出
只写 `OK` 加换行；不匹配、文件访问失败与输出失败的规则都与
`check-digest` 相同（见上一节）：不匹配时退出码 `1`、标准输出为空、
标准错误列出小写的预期摘要与实际摘要；待核对文件无法访问时报文件原因，
不会给出部分摘要或称为不匹配。两个路径都按操作系统给出的原始路径
处理，输出失败规则同样沿用现有约定。

### 摘要文件的格式

摘要文件只允许包含**一份**摘要：恰好 64 个 ASCII 十六进制字符
（`0-9`、`a-f`、`A-F`，大小写可混用，按其表示的值比较），文件末尾
可以没有换行，也可以有一个 LF 或一个 CRLF——因为 `digest > 文件`
写出的摘要行本身就带一个 LF，所以这份输出可以直接作为摘要文件使用。

除此之外不做任何裁剪或修正：空文件、首尾空格、单独的 CR、额外空行、
第二份摘要、附带的文件名、`0x` 之类前缀或非 ASCII 字节都属于格式
错误。命令不会只取第一行而忽略其后的内容；含有多余字节的文件一律
拒绝。

**与 `check-digest` 摘要参数的区别**仅在文件末尾换行这一点上：

- `check-digest <文件> <摘要>` 的摘要是命令行参数，必须恰好是 64 个
  十六进制字符，末尾带一个换行就是 65 个字节，属于用法错误。
- `check-digest-file <文件> <摘要文件>` 的摘要来自文件，允许上述 64
  个字符之外再跟一个 LF 或 CRLF；除这一个行结束之外的任何字节仍按
  格式错误处理。库接口（`Sha256Digest::from_hex_bytes` / `FromStr`）
  的严格解析规则也保持不变，不会因为新命令而放宽。

### 先处理摘要文件

命令先完整处理摘要文件，确认其可以打开、读取且格式合法之后，才访问
待核对文件：

- 摘要文件格式错误：退出码 `2`，标准输出为空，标准错误指出摘要文件
  路径与具体格式问题并给出新命令的用法；此时即使待核对文件不存在，
  也不会改报它的访问错误。
- 摘要文件不存在、指向目录、无法打开或读取中途失败：退出码 `1`，
  标准输出为空，标准错误指出摘要文件及原因（`cannot open digest file`
  或 `cannot read digest file`），不进入内容比较。
- 缺少或多给参数：与其他命令一样属于用法错误（退出码 `2`）。

## Rust 库接口

库提供与命令行同一内容规则的摘要计算：

```rust
use inkseal::digest_reader;

let digest = digest_reader(std::io::empty()).unwrap();
assert_eq!(
    digest.to_hex(),
    "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
);
```

`digest_reader` 接受任何实现 `std::io::Read` 的输入，成功时返回
`Sha256Digest`（可用 `to_hex()` 或 `Display` 得到与命令行一致的十六
进制文本）；读取失败时返回类型化的 `DigestError`，不会把失败当作
成功摘要。密码运算基于 `sha2`（RustCrypto）实现。

### 从文本还原已保存的摘要

`Sha256Digest` 实现了标准库的 `FromStr`，调用方可以用 Rust 常规的
字符串解析方式（`str::parse` 或 `Sha256Digest::from_str`）把先前保存
的摘要文本还原成摘要对象，与计算结果直接比较：

```rust
use inkseal::{digest_reader, Sha256Digest};

let computed = digest_reader(&b"abc"[..]).unwrap();
let saved = "ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad";
let restored: Sha256Digest = saved.parse().unwrap();
assert_eq!(restored, computed);
```

解析结果与计算结果是同一类型，`as_bytes()`、`to_hex()` 和 `Display`
都可直接使用；输出仍然是 64 个小写十六进制字符（保留前导零）。

**格式是严格的**：输入必须恰好是 64 个 ASCII 十六进制字符。`0-9`、
`a-f`、`A-F` 均可，大小写混用表示同一个摘要。解析不做任何裁剪或
修正——首尾空白、末尾换行、`0x` 前缀、分隔符，以及全角数字或字母
等非 ASCII 内容都属于格式错误；空字符串也不会被当作空文件的摘要。

解析失败时得到公开的类型化错误 `ParseDigestError`，两类失败可按
变体区分：

- `ParseDigestError::InvalidLength(n)`：输入的 UTF-8 字节长度不是
  64，`n` 是实际字节长度（也可用 `actual_length()` 取得）。注意
  长度按字节数判断，全角字符一个字符占多个字节。
- `ParseDigestError::InvalidHexChar(pos)`：长度正确但含非法字符，
  `pos` 是首个非法字节从零开始的字节偏移（也可用
  `invalid_position()` 取得），按原始文本的字节计算，不按字符个数。

该错误实现了 `Display` 和 `std::error::Error`，可直接显示或装入
`Box<dyn Error>` 传递。

## 导入 Ed25519 公钥

除摘要计算外，库还提供独立的 Ed25519 公钥类型与导入入口
`import_ed25519_public_key`。调用方传入的是一份**二进制公钥容器**——
DER 编码的 SubjectPublicKeyInfo（RFC 5280 的 `SubjectPublicKeyInfo`
结构，算法遵循 RFC 8410）的原始字节，例如整个读自一个 `.der` 文件或
网络消息：

```rust
use inkseal::import_ed25519_public_key;

// 传入的是二进制公钥容器（DER 字节），不是十六进制文本或 PEM 文本。
let spki = std::fs::read("peer-ed25519-public.der").unwrap();

let public_key = match import_ed25519_public_key(&spki) {
    Ok(key) => key,
    Err(err) => panic!("rejected: {err}"),
};

// 原样读取 32 字节公钥；两个公钥可用 == 比较是否相同。
let raw: &[u8; 32] = public_key.as_bytes();
assert_eq!(raw.len(), 32);
let again = import_ed25519_public_key(&spki).unwrap();
assert_eq!(public_key, again);

// 文本表示固定为 64 个小写十六进制字符，保留前导零，不含标签或换行；
// 它表示公钥本身，不是公钥的 SHA-256 摘要。
println!("{public_key}");
```

一份最小的 Ed25519 公钥容器共 44 字节：

```text
30 2a 30 05 06 03 2b 65 70 03 21 00 <32 字节公钥>
```

其中 `06 03 2b 65 70` 是算法 OID `1.3.101.112`（Ed25519），
`03 21 00` 引出一个未使用位数为零的 BIT STRING，其后恰好是
32 字节公钥。

### 公钥类型与摘要类型明确区分

成功时返回的是独立类型 `Ed25519PublicKey`，与 `Sha256Digest` 没有
共同的构造或转换入口：公钥只能从二进制 SPKI 导入，不能从十六进制
文本构造，也不会被当作摘要解析；即使某把公钥的 32 字节恰好等于某个
摘要的 32 字节，二者仍是不同类型、不同语义。公钥的 `to_hex()` /
`Display` 与摘要形状相同（都是 64 个小写十六进制字符、保留前导零），
但它是**公钥字节本身**的文本表示，不是对公钥再做一次 SHA-256 的
结果。

### 接受与拒绝范围

接受范围严格遵循 RFC 8410 对 Ed25519 公钥的规定：

- 算法标识必须是 `1.3.101.112`；
- 算法参数必须**缺省**——即使显式写成 `NULL`（`05 00`）也按非法
  公钥拒绝，不会当作缺省参数；
- 公钥所在 BIT STRING 的未使用位数必须为零；
- 公钥内容必须恰好 32 字节。

输入必须是一份**完整、规范的 DER 对象**。截断数据、声明长度与实际
内容不符、非规范长度编码（如用长形式表示小于 128 的长度、长形式带
前导零、BER 的不确定长度）、容器中出现多余字段（AlgorithmIdentifier
多出参数、外层 SEQUENCE 多出成员）或对象之后还有字节，都会被拒绝：
不会忽略剩余内容，也不会自动补齐缺失字段。

裸 32 字节公钥、公钥的十六进制文本以及 PEM 文本（`-----BEGIN
PUBLIC KEY-----`）都**不属于**这个入口接受的格式；入口不做格式猜测、
不剥 PEM 头、也不做十六进制或 Base64 文本转换。需要这些形态时，
调用方应先自行确定格式并完成去封装，再把其中的 DER 字节交给本入口。

### 类型化的导入错误

导入失败返回公开的类型化错误 `KeyImportError`，调用方无需分析提示
字符串就能区分两类失败：

- `KeyImportError::Malformed`：编码或公钥结构不合法——包括空输入、
  截断、长度不符、非规范长度编码、多余字段或尾随字节、参数非缺省、
  位串未使用位非零、公钥长度不是 32 字节，以及裸公钥/十六进制/PEM
  等非本入口格式。
- `KeyImportError::UnsupportedAlgorithm(algorithm)`：SubjectPublicKeyInfo
  结构完整、DER 合法，但算法标识不是 Ed25519。携带的
  `PublicKeyAlgorithm` 保留了实际标识：`PublicKeyAlgorithm::Ed25519`
  是唯一受支持值；其他算法可通过 `oid_bytes()` 取得其 OID 的原始
  DER 内容字节自行解码展示，库不猜测它的文本名称。

只有“结构完整、DER 合法”时才可能报算法不支持；整体编码已经损坏时
一律报 `Malformed`，不会因为损坏数据中局部恰好出现某个其他算法的
OID 字节就改报算法不支持。任何失败都不会产出可继续使用的公钥对象，
解析过程也不会在任意输入上崩溃。该错误实现了 `Display` 和
`std::error::Error`。

### 导入成功的含义

**导入成功只表示这份 DER 编码被接受**：公钥容器结构完整、算法确为
Ed25519、公钥字节长度正确。它**不**表示已经用这把公钥验证过任何
文件或消息的签名，也**不**确认公钥持有者的身份。确认身份需要调用方
通过带外的信任渠道完成；验证签名需要另行使用 Ed25519 签名验证机制，
二者都不在导入入口的职责范围内。
